# Fintech Operations Console — Prototype Feature Spec

## Purpose

Build a two-hour prototype showing how a Devin-built internal tool can provide a more useful, task-specific experience than a generic record dashboard.

The prototype covers three internal workflows:

1. KYC review
2. Refund operations
3. Feature-flag administration

The prototype is intentionally limited to the employee-facing application layer. It uses synthetic data and simulated actions. It does not attempt to reproduce production identity, Dataverse, Power Automate, compliance infrastructure, or integrations with real fintech systems.

## Product thesis

A custom application should not give every record the same visual weight or force operators to hunt through a standard form. It should use the context already present in the data to answer three questions immediately:

1. What needs my attention?
2. Why does it need my attention?
3. What should I do next?

The interface should adapt its emphasis to the record. The complete data remains available, but the most consequential evidence appears first.

This is an attention hierarchy, not an automated decision system. The prototype may rank and present risk signals, but it must not imply that the UI independently makes compliance or financial decisions.

## Shared application shell

### P0 — Required

- Unified left navigation for KYC, Refunds, and Feature Flags
- Consistent tables, badges, filters, detail views, dialogs, and activity timelines
- Desktop-first responsive layout
- Synthetic data with realistic variation
- Search, filtering, and sorting in each module
- A mock signed-in user and clearly labeled role switcher
- Prominent environment indicator where an action can affect production
- Confirmation dialog for consequential actions
- Toast or inline feedback after actions
- Activity events generated by user actions
- Thin service interface between UI components and mock data

### P1 — If time permits

- Local persistence across browser refreshes
- Global activity page combining events from all three modules
- Saved or persistent filters
- Loading, empty, and recoverable error states
- Keyboard shortcuts for high-frequency review actions

## Adaptive presentation system

All three modules should follow the same pattern:

1. Each record contains structured signals describing urgency, severity, confidence, and evidence.
2. The application selects a primary review focus using deterministic display rules.
3. A type-specific focus panel presents the most relevant evidence and action.
4. Secondary signals are visible immediately below it.
5. Complete record data remains available through clearly labeled sections or tabs.

The prototype should make these display rules explainable. A reviewer should be able to see why a signal was highlighted.

The presentation layer must not silently change the underlying risk or eligibility result. It only changes which information is emphasized.

# Module 1: KYC Review

## Goal

Help a reviewer understand the central risk in a case within seconds, without making every customer profile look like the same generic compliance form.

## KYC operations overview

The module landing page should show the health of the entire review operation, not only the current reviewer’s assignments. This helps an operator or manager understand the remaining workload and whether the queue is improving.

### P0 — Required

- Total cases left to review
- Cases received today
- Cases completed today
- Cases currently overdue
- Average review time, with comparison to the previous period
- Oldest unreviewed case
- Backlog split by risk level
- Review-time trend over a meaningful recent period, such as the last 14 or 30 days
- Received-versus-completed trend so the viewer can tell whether the backlog is growing

The dashboard should prioritize actionable workload questions rather than decorative metrics:

- Are reviews keeping up with new cases?
- How much work remains?
- Is review time getting better or worse?
- Which risk band or age band is causing the backlog?

### P1 — If time permits

- Backlog split by age or SLA band
- Estimated time to clear the queue at the recent completion rate
- Filters for time period, risk level, or review status
- Click a metric or chart segment to apply that filter to the queue

## KYC queue

### P0 — Required

- Search by customer name or case ID
- Filter by review status, risk level, and assignee
- Sort by oldest, newest, highest risk, or nearest SLA breach
- “Assigned to me” shortcut
- Queue columns:
  - Case ID
  - Customer
  - Country
  - Overall risk
  - **Review focus**
  - Status
  - Assignee
  - Age or SLA
- Visually distinguish overdue and high-risk cases
- Selecting a row opens the case detail experience

The **Review focus** column should summarize the record-specific reason for review, such as “Possible sanctions match,” “Document inconsistency,” or “Duplicate identity.” This makes the queue actionable before a case is opened.

## KYC case detail

### P0 — Required

- Adaptive review header containing:
  - Overall risk
  - Primary review focus
  - Why it was highlighted
  - Signal confidence or strength when available
  - Suggested evidence to inspect
- Secondary risk signals ordered by severity
- High-level financial picture that can be understood without expanding every section
- Expandable customer profile, financial activity, verification, document, and relationship sections
- Customer profile
- Verification results
- Submitted-document metadata
- Internal notes
- Review and activity history
- Approve, reject, request information, and add note actions
- Required reason for rejection or request-information actions
- Confirmation before a decision is applied
- Activity event after every action

## Customer financial picture

The case overview should summarize the whole customer relationship before asking the reviewer to inspect individual records. Use synthetic values for:

- Account age and account status
- Current balances by account or product
- Recent inflows and outflows
- Typical monthly transaction volume
- Declared income, occupation, and source of funds
- Observed activity compared with the declared profile
- Primary transaction geographies
- Largest or unusual counterparties
- Cash, card, bank-transfer, or crypto exposure when applicable
- Prior alerts, disputes, restrictions, or reviews

The summary should call out material inconsistencies, such as observed monthly inflows being several times higher than declared income, while avoiding unsupported conclusions.

## Progressive disclosure

The detail view should provide a complete high-level picture above the fold, followed by expandable sections. Expanding a section should reveal the evidence needed for deeper review without navigating away from the case.

Suggested expandable sections:

- Identity and customer profile
- Accounts and balances
- Transaction activity
- Source of funds and expected activity
- Counterparties and geographic exposure
- Verification results
- Documents
- Linked identities and devices
- Notes and activity

If a section contains the primary risk signal, it should open by default and receive stronger visual emphasis. Unrelated sections should remain collapsed but show a compact status summary, such as “3 checks passed” or “1 item needs review.”

## Type-specific KYC focus panels

The detail page should render a different primary panel based on the highest-priority signal.

### Possible sanctions or PEP match

Emphasize:

- Side-by-side customer and watchlist identity
- Matching and conflicting fields
- Name-match strength
- Date of birth and nationality comparison
- Source list and result timestamp
- Clear false-positive or escalate path

### Identity or document mismatch

Emphasize:

- Side-by-side submitted and extracted values
- Fields that disagree
- Document validity and expiration
- Extraction confidence
- Document or metadata anomalies

### High-risk jurisdiction

Emphasize:

- Relevant countries and customer connections
- The policy or rule that produced the signal
- Source of address, residency, or nationality data
- Other risk factors that strengthen or weaken the concern

### Duplicate or linked identity

Emphasize:

- Potentially related customer records
- Shared email, phone, device, address, or identity attributes
- Strength of each relationship
- Status of related accounts or prior reviews

### Address verification failure

Emphasize:

- Submitted, normalized, and verified address values
- Exact mismatching components
- Verification-provider response
- Document recency and evidence source

### No dominant risk signal

Emphasize:

- Compact verification checklist
- Any incomplete evidence
- Clear explanation that no single signal dominates
- Normal review path without manufacturing urgency

## KYC data shape

Each synthetic case should support a structure similar to:

```text
case
  id
  customer
  status
  assignee
  submittedAt
  slaDueAt
  overallRisk
  riskSignals[]
    type
    severity
    confidence
    headline
    explanation
    evidence[]
    source
  profile
  financialSummary
  accounts[]
  transactionSummary
  counterparties[]
  verificationResults[]
  documents[]
  notes[]
  activity[]
```

The mock focus-selection rule can rank signals by severity and then confidence. Production rules would need to come from the company’s compliance and risk teams.

## KYC demonstration cases

Seed at least five deliberately different cases:

1. A possible sanctions match
2. A document/profile mismatch
3. A high-risk jurisdiction case
4. A possible duplicate identity
5. A low-risk case with incomplete evidence but no dominant signal

The cases should visibly produce different detail-page emphasis while retaining a consistent application structure.

## KYC P1 enhancements

- Next-case navigation that respects the current queue filter
- Side-by-side evidence review
- Assign or reassign case
- Persistent reviewer filters
- Keyboard-friendly approve, reject, and next-case flow

# Module 2: Refund Operations

## Goal

Show the operational context that matters for the specific refund rather than presenting every request as the same payment record.

## Refund dashboard and queue

### P0 — Required

- Summary metrics:
  - Requests today
  - Total requested amount
  - Pending review
  - Average processing time
  - Failure rate
- One useful visualization, such as seven-day refund volume
- Search by refund ID, payment ID, or customer
- Filter by status, reason, amount, or risk
- High-value-only shortcut
- Queue columns:
  - Refund ID
  - Customer
  - Amount
  - Reason
  - **Review focus**
  - Status
  - Requested time

## Adaptive refund detail

The primary panel should change based on the operational issue:

- **High value:** emphasize approval threshold, required approvers, and remaining approval
- **Possible duplicate:** emphasize related refund attempts and overlapping amounts
- **Elevated fraud signal:** emphasize account and refund velocity, prior disputes, and risk evidence
- **Processor failure:** emphasize error category, retry state, and whether funds moved
- **Normal request:** emphasize original payment, eligibility, reason, and standard decision path

## Behavioral context for each refund

Every refund detail should put the request in two comparison frames: the customer’s prior behavior and the behavior associated with the item, merchant, product, or refund type.

### Customer-level context

Show:

- Number and value of prior refund requests
- Refund rate relative to completed purchases or payments
- Time since the previous refund
- Refund reasons over time
- Prior disputes or chargebacks
- Account age and recent purchase activity
- Comparison with a relevant customer cohort
- A plain-language summary, such as “4th refund in 30 days; typical for this cohort is 0–1”

### Item-, merchant-, or refund-type context

Show whichever level is meaningful for the synthetic transaction:

- Frequency of refunds for the same item, merchant, category, or reason
- Refund rate compared with the platform baseline
- Common reasons for similar refunds
- Recent spike or change in frequency
- Whether other customers reported the same issue
- A plain-language summary, such as “This item’s refund rate is 18%, versus 3% for its category”

### Presentation rules

- Lead with customer behavior when the user is the unusual factor
- Lead with item or merchant behavior when the request resembles a broader product issue
- Show both views when they materially disagree
- Explain the comparison group and time period
- Treat these metrics as decision context, not automatic proof of abuse or eligibility

### P0 actions

- Approve
- Reject with required reason
- Escalate
- Add internal note
- Clearly distinguish approval from successful payment-processor completion
- Generate activity events

### P1 safeguards

- Simulated dual approval for high-value refunds
- Prevent the same mock user from providing both approvals
- Completed refunds are read-only
- Simulated failure and retry state

# Module 3: Feature-Flag Administration

## Goal

Make a flag understandable in terms of actual developer usage, effective user behavior, blast radius, and product intent—not only as an enabled/disabled configuration record.

## Feature-flag list

### P0 — Required

- Search by flag name or key
- Filter by environment, enabled state, owner, or health
- Stale-flags shortcut
- Columns:
  - Flag
  - Environment
  - Enabled state
  - Rollout
  - **Operational focus**
  - Owner
  - Last updated

## Adaptive flag detail

The primary panel should change based on the flag’s operational state:

- **Production with broad exposure:** emphasize blast radius, affected percentage, and owner
- **Recent or risky change:** emphasize before/after configuration and recent activity
- **Stale flag:** emphasize age, permanent state, owner, and cleanup recommendation
- **Scheduled rollout:** emphasize timeline, current stage, next transition, and rollback condition
- **Dependent flag:** emphasize prerequisites and downstream flags or services
- **Development flag:** use a lighter-weight editing path while retaining an environment indicator

The detail page must distinguish:

- The flag’s default value
- Environment-level configuration
- Percentage rollout
- User or group targeting rules
- Personal overrides
- The final effective value for a selected user

Simply labeling a flag “on” or “off” is insufficient when targeting rules or overrides exist.

## Code usage and developer integration

### P0 — Required

- List every synthetic code location where the flag is evaluated or referenced
- For each location show:
  - Repository
  - Branch or commit
  - File path and line number
  - Language
  - Code snippet with the flag reference highlighted
  - Usage type, such as evaluation, fallback, experiment exposure, test, or cleanup
  - Last modified time and author when available
- “Open in Devin” action for each code location
- Copyable repository path and line reference
- Summary of code footprint, such as repositories, services, and total references

For the prototype, code references and the Devin action may use synthetic repository data and a clearly labeled simulated integration. A production implementation would require repository indexing, authorization, current commit information, and a supported Devin handoff or deep-link mechanism.

### P1 — If time permits

- Group references by service or repository
- Show related tests and whether the enabled and disabled paths appear to be covered
- Indicate stale references that may be safe to remove
- “Ask Devin about this flag” action that starts with the flag, repository, and selected code location in context

## Effective-flag debugger

### P0 — Required

- Input a synthetic user ID
- Display every relevant flag and its effective value for that user
- Search and filter the result set
- For an individual flag, show an evaluation trace:
  1. Environment default
  2. Global state
  3. Matching group or segment
  4. Percentage rollout result
  5. User-specific override
  6. Final effective value
- Explain which rule determined the result
- Make it easy to copy the debugging summary

This is a simulation of flag evaluation. The production version would need to use the same evaluation semantics and context attributes as the runtime SDK to avoid showing a misleading result.

## Personal and targeted flag controls

### P0 — Required

- “My flags” view showing the effective flags for the mock signed-in user
- Easily enable or disable an allowed personal override
- Make the scope and expiration of the override visible
- Add or remove a synthetic user from a flag’s targeting rule
- Target a synthetic group or segment
- Preview the affected audience before saving
- Require a reason and confirmation for changes

Personal overrides should be visually distinct from global or production configuration. The prototype should demonstrate that a developer can safely test a feature for themselves without accidentally enabling it for everyone.

### P1 safeguards

- Time-limited overrides with automatic expiration
- Warn about conflicting or shadowed rules
- Production targeting changes require elevated mock permissions
- Show the number and percentage of users affected by a proposed change

## Feature context and supporting materials

Each flag detail should explain the product behavior the flag controls:

- Plain-language feature description
- Owning team and responsible engineer
- Lifecycle state: development, rollout, permanent, rollback, or cleanup
- Creation date and expected removal date
- Links to synthetic product requirements, design documents, tickets, and runbooks
- Before/after screenshot or small visual preview where useful
- Rollout and rollback criteria
- Known dependencies and affected services

This context should appear alongside configuration and code usage so an engineer can understand both what the flag does and how it is implemented.

## Flag actions

### P0 — Required

- Enable or disable
- Change rollout percentage
- Require a change reason
- Show a before-and-after diff
- Confirm before applying
- Generate an activity event

### P1 safeguards

- Strong production banner
- Typed confirmation or explicit production checkbox
- Simulated approval requirement for high-blast-radius changes
- One-click simulated rollback to the previous configuration

# Roles

Use three simulated roles to demonstrate interface behavior. Clearly label this as UI simulation, not production authorization.

| Role | KYC | Refunds | Feature Flags |
| --- | --- | --- | --- |
| Viewer | Read | Read | Read |
| Operator | Review cases | Review standard refunds | Change non-production flags |
| Admin | Reassign or override | Provide high-value approval | Change production flags |

# Activity model

Each meaningful action should create an activity record containing:

- Actor
- Action
- Record type and ID
- Timestamp
- Reason or note
- Before and after values when applicable

The UI may call this an activity history or audit-style timeline. It must not claim to be immutable or compliance-grade.

# Prototype non-goals

- Real authentication or SSO
- Server-enforced authorization
- Real PII or customer data
- Real KYC-provider integration
- Document upload or storage
- Real payment or refund execution
- Real feature-flag-provider integration
- Real repository indexing or code search
- A production Devin deep-link or authenticated handoff
- A runtime-compatible feature-flag evaluation engine
- Background jobs, queues, retries, or notifications
- Tamper-resistant audit storage
- Production monitoring or incident response
- Compliance certification
- Full Power Apps, Dataverse, or Power Automate replacement

# Two-hour cut line

Implement in this order:

1. Shared shell and synthetic data
2. KYC workload overview, queue, and adaptive financial case detail
3. Feature-flag detail with code references, user debugger, and personal override
4. Refund queue with customer- and item-level behavioral context
5. Consequential actions, confirmations, and shared activity
6. Additional flag controls, persistence, and polish only if time remains

If the timebox becomes tight, preserve the adaptive KYC experience and the developer-aware feature-flag detail first. The central demonstration is not the number of screens; it is that a custom application can shape itself around an operator’s or developer’s decision context.

# Prototype success criteria

The prototype succeeds if a viewer can:

1. Understand the size, age, and direction of the overall KYC workload.
2. Open multiple KYC cases and immediately see different evidence emphasized for each one.
3. Capture the customer’s overall financial picture, then expand the evidence relevant to the primary concern.
4. Understand whether a refund looks unusual for the customer, the item or merchant, both, or neither.
5. Open a flag and understand what feature it controls, where it appears in code, and what its effective value is for a selected user.
6. Enable a safe personal override without confusing it with the global production state.
7. Complete at least one consequential action with an appropriate confirmation and activity event.
8. Understand which parts are frontend demonstrations and which production capabilities remain outside scope.
